先答旧题
RIP、OSPF、BGP 分别封装在什么里？
UDP、IP、TCP。
RIP 最大距离？不可达用什么表示？
15；16。
距离向量更新时，来自当前下一跳的信息怎么处理？
一律采用，即使距离变大。

IP 把分组送到了主机，可主机上跑着很多程序，这个分组给谁？而且 IP 不可靠，丢了怎么办？这就是传输层的两件事：把数据交给正确的进程，以及（TCP）让通信可靠。这一话讲 UDP 和 TCP 怎么建立、结束连接，下一话讲 TCP 怎么保证可靠。

其之壹传输层干什么

网络层是主机到主机，传输层是进程到进程（端到端）。一台主机上多个进程共用网络，发送时汇集叫复用，接收时分发叫分用，都靠端口。

套接字（socket）= IP + 端口，标识一个通信端点。

术式
端口

熟知端口（0–1023）：20/21 FTP、23 Telnet、25 SMTP、53 DNS、69 TFTP、80 HTTP、110 POP3、143 IMAP、161 SNMP、443 HTTPS。
登记（1024–49151）；动态（49152–65535）。
TCP 用四元组（两端 IP:端口）标识连接；UDP 只用目的 IP 和目的端口分用。

其之貳UDP

只在 IP 上加了端口和校验。没有握手、没有确认、没有重传。

术式
UDP 特点

无连接、尽力交付、面向报文（不拆不合）、无拥塞控制、首部 8 B。适合实时音视频、DNS。

既然不可靠，为什么还要？首部小、没有连接开销、丢了也不影响实时音视频；应用可以自己做可靠性。

校验和怎么算

校验和要覆盖 UDP 首部和数据，还要在前面临时加一个 12 字节的伪首部（源 IP、目的 IP、协议号、UDP 长度）。伪首部不发送，只用于计算。它让接收方能发现「分组送错了地方」。

算法：

  1. 校验和字段先置 0，全部数据按 16 位分组（奇数字节补 0）。
  2. 把所有 16 位按反码相加（高位进位加回低位）。
  3. 取反，放入校验和字段。
  4. 接收方把全部（含校验和）反码相加，结果全 1 才正确。

例：两个 16 位数 0x8000 和 0x8001。相加得 0x1 0001，进位加回得 0x0002，取反得 0xFFFD。

UDP 校验和在 IPv4 中可选（全 0 表示不校验）。TCP 用同样的算法，但必须校验。它只能发现错误，发现就丢弃，不保证可靠。

其之參TCP 首部

TCP 把应用数据看成字节流，每个字节都有序号。面向连接、可靠、全双工、点对点。

术式
字段语义

seq：本段数据的第一个字节的序号。
ack：期望收到的下一个字节的序号（累积确认），ACK=1 才有效。
SYN、FIN 各占一个序号。
纯 ACK 不占序号。
MSS：最大段长，只算数据部分，握手时协商。

走一遍序号：甲发 seq=100，带 200 字节，下一段 seq=300。乙全收到就回 ack=300，意思是「300 之前我都有了，下面要 300」。

如果甲连发三段（100、300、500），第二段丢了：乙收到第一段回 ack=300；收到第三段时第二段还没到，仍回 ack=300。累积确认只确认连续的部分。

双向传数据时，甲发出的 seq 等于乙最后的 ack，甲发出的 ack 等于乙的 seq 加乙的数据长度。

标志位：SYN 建连、FIN 释放、ACK 确认有效、RST 复位（异常，立即断开）、PSH 尽快交给应用、URG 紧急。

合上页面说一遍：seq 和 ack 分别是什么？SYN 占序号吗？纯 ACK 呢？

seq 是本段第一个字节的序号；ack 是期望的下一字节。SYN、FIN 占一个序号；纯 ACK 不占。

其之肆三次握手

建立连接要交换初始序号，并确认双方的收发都正常。

术式
握手要点

为什么三次：确认双方的发送和接收都正常，防止旧的连接请求造成错误。如果只有两次，一个滞留的旧 SYN 到达后，服务器就会白白建立连接。
服务器的资源：第二次握手后分配（SYN 洪泛攻击就利用这一点）。
状态：LISTEN → SYN-RCVD → ESTABLISHED。

序号为什么不从 0 开始？防止和旧连接的序号混淆。

其之伍四次挥手

TCP 全双工，两个方向要分别关闭。

中间的 ACK 和 FIN 能不能合并？能。如果服务器也没数据要发，就是三次。

半关闭：一方说「我不发了」，对方还可以继续发，它还能收。

术式
为什么要 TIME-WAIT

① 保证最后一个 ACK 到达（丢了对方会重发 FIN，可以重发 ACK）。② 让本连接的旧报文都消失，不干扰新连接。
TIME-WAIT = 2MSL，主动关闭方才有。

术式
连接管理的时间（以 RTT 计）

建立：发起方收到第二次握手 = 1 RTT，此后就能发数据；对方收到第三次握手 = 1.5 RTT。
释放（对方立即回 FIN+ACK 的最快情况）：对方进入 CLOSED = 1.5 RTT；发起方进入 CLOSED = 1 RTT + 2MSL。

合上页面说一遍：不看图，写出三次握手的 SYN、ACK、seq、ack。TIME-WAIT 的两个理由？

SYN=1,seq=x；SYN=1,ACK=1,seq=y,ack=x+1；ACK=1,seq=x+1,ack=y+1。保证最后的 ACK 能到；让旧报文消失。

领域展开

首部：seq 第一字节，ack 期望下一字节；SYN、FIN 占序号。
握手：SYN，SYN+ACK，ACK（可带数据）。
挥手：可能半关闭；TIME-WAIT 等 2MSL。
UDP：8 字节，伪首部参与校验。

2014實戰UDP 三性质 · 差错检验与可靠传输
下列关于 UDP 的叙述中，正确的是（　）。
Ⅰ. 提供无连接服务　Ⅱ. 提供复用/分用服务　Ⅲ. 通过差错检验，保障可靠数据传输

UDP 提供无连接服务（Ⅰ 正确），并在发送/接收时通过端口号实现复用与分用功能（Ⅱ 正确）。虽然 UDP 首部包含检验和字段用于差错检测，但其仅能发现传输错误并丢弃出错报文，不具备重传、确认等机制，无法保障可靠数据传输，可靠性需由应用层实现。因此说法 Ⅲ 错误。
差错检验只能发现错，不能保证可靠。
再深一层
选 B。本题就是「UDP 相对 IP 的两项增量」的原样考法：Ⅰ、Ⅱ 是它有的，Ⅲ 越界了。
UDP 有：无连接 ✅　复用/分用 ✅　差错检测 ✅
UDP 无：确认 ❌　重传 ❌　排序 ❌　流量控制 ❌　拥塞控制 ❌
⚠️⚠️ Ⅲ 的措辞极其精细，是本题的全部难度所在：它没说「UDP 不检错」（那样就明显错了），而是说「通过差错检验保障可靠传输」——把「检错」偷换成了「可靠」。检错只能发现问题然后丢弃；可靠还需要「发现之后能补救」，即确认 + 重传。UDP 缺的正是补救那一步。
📌 一句判据：可靠 = 检错 + 确认 + 重传。少任何一项都不叫可靠。（与 5.1.1-07「可靠的判据是确认机制」互为印证。）
🔗 同年考点追踪：2014 年在本节还标注了「UDP 协议的优点」，与 2024 一起构成「UDP 优点」的两次命中——见 5.2.1-09。
2018實戰分用的依据
UDP 实现分用时所依据的首部字段是（　）。

传输层的分用是指接收方根据报文首部信息将数据交付给正确的应用进程。UDP 使用目的端口号标识目标进程，是分用的关键依据。源端口号主要用于回信，非分用所必需；长度和检验和字段不参与进程寻址。
再深一层
选 B。分用是「接收方向上交付」的动作，当然看目的端口号。
字段干什么用的参与分用吗
目的端口号指明本报文该交给哪个进程✅ 就是它
源端口号「返回地址」，供对方回信；不需要回复时可置全 0❌
长度首部 + 数据的字节数❌
检验和差错检测❌
📌 「源端口可以置全 0」这一条本身就是本题的最强反证：一个可以整个置 0 的字段，绝不可能是分用必需的依据。
📌 把三层的分用依据连起来背：帧的「类型」→ IP 的「协议」→ UDP/TCP 的「目的端口号」，一条自底向上的交付链，每一层都靠本层首部里的一个字段找到上一层的实体。
2009實戰连续两段的累积确认
主机甲与主机乙之间已建立一个 TCP 连接，主机甲向主机乙发送了两个连续的 TCP 段，分别包含 300B 和 500B 的有效载荷，第一个段的序号为 200，主机乙正确接收到这两个数据段后，发送给主机甲的确认序号是（　）。

确认序号表示接收方期望收到的下一个字节的序号。第一个段起始序号为 200，包含 300B 数据，序号范围 200～499；第二个段起始序号为 500，包含 500B 数据，序号范围 500～999。因此，乙正确接收后，期望的下一个字节序号为 1000，故返回的确认序号为 1000。
200+300+500 = 1000。
再深一层
🐍 Python 复算 200 + 300 + 500 = 1000，与书答吻合，选 D。
段1：seq＝200，300B ⟹ 覆盖 200 ～ 499
段2：seq＝500，500B ⟹ 覆盖 500 ～ 999
两段都收到 ⟹ ack ＝ 999 ＋ 1 ＝ 1000
⚠️ 四个干扰项逐个溯源：
选项它是什么
A 500只确认了第 1 段（200+300）
B 700把两段长度弄反或只加了一部分
C 800300 ＋ 500 ＝ 800，忘了加起始序号 200 ← 最强干扰项
D 1000200 ＋ 300 ＋ 500 ✅
⭐ 母公式（本节所有序号题共用）：ack ＝ 第一个段的 seq ＋ 已连续收到的字节总数。注意「已连续收到」——一旦中间有缺口，就只能算到缺口为止（见 5.3.4-02 与 2011 真题）。
📌 本题与 2011 真题（5.3.4-05）是一对：本题「全收到」⟹ 累加到底；2011「中间丢一段」⟹ 只能确认到缺口。两题连着做，累积确认的边界就清楚了。
2011實戰缺口处的累积确认
主机甲与主机乙之间已建立一个 TCP 连接，主机甲向主机乙发送了 3 个连续的 TCP 段，分别包含 300B、400B 和 500B 的有效载荷，第 3 个段的序号为 900。若主机乙仅正确接收到第 1 个段和第 3 个段，则主机乙发送给主机甲的确认序号是（　）。

TCP 段的序号字段表示该段数据部分第一个字节的序号。已知第 3 个段序号为 900，则第 2 个段的结束序号为 899，起始序号 = 900−400 = 500。主机乙仅收到第 1 段和第 3 段，未收到第 2 段（500～899），因此期望收到的下一个字节序号为 500，即确认序号为 500。
第 3 段序号 900，长度 500，第 2 段序号 500。乙收到 1、3 段：第 1 段结束 500，确认 500。
再深一层
🐍 Python 复算 900 − 400 = 500，与书答吻合，选 B。
段1：300B  序号 200 ～ 499   ✅ 收到
段2：400B  序号 500 ～ 899   ❌ 丢失 ← ack 就停在这里
段3：500B  序号 900 ～ 1399  ✅ 收到，但失序，只能缓存
⚠️⚠️ 最大的坑：减去的是第 2 段自己的长度 400，不是第 3 段的 500。关系式是「段3.seq = 段2.seq + 段2.长度」⟹ 段2.seq = 900 − 400 = 500。减成 900 − 500 = 400 就全盘皆错。
⚠️ C（1200）与 D（1400）是给「以为可以确认到第 3 段末尾」的人准备的：TCP 是累积确认，一旦中间有洞，后面收得再多也不能确认。（1400 恰好是第 3 段的末字节 +1，看起来很像答案，其实完全用不上。）
⭐ 与 2009 真题（5.3.4-04）的对照：
20092011
接收情况全部收到中间丢一段
ack一路累加到最后 ⟹ 1000停在第一个缺口 ⟹ 500
📌 顺带一提：第 3 段的到达会让乙立即发一个冗余 ACK（ack=500），这就是快重传机制的起点。
2013實戰双向报文段的 seq 与 ack
主机甲与主机乙之间已建立一个 TCP 连接，双方持续有数据传输，且数据无差错与丢失。若甲收到一个来自乙的 TCP 段，该段的序号为 1913、确认序号为 2046、有效载荷为 100B，则甲立即发送给乙的 TCP 段的序号和确认序号分别是（　）。

乙发送给甲的 TCP 段中，序号 seq=1913 表示其数据从字节编号 1913 开始，有效载荷为 100B，故覆盖 1913～2012；确认序号 ack=2046 表示乙已成功接收甲发送的序号至 2045 的所有数据，期望下个字节为 2046。甲成功收到后，在立即回复的 TCP 段中，seq 应置为 2046（发送的第一个字节序号），ack 应置为 2013（期待乙发送的下一个字节序号，即 2012+1）。
甲发的 seq = 对方的 ack = 2046；ack = 1913 + 100 = 2013。
再深一层
🐍 Python 复算：seq = 2046，ack = 1913 + 100 = 2013，与书答吻合，选 B。本题是「两个方向各算一遍」的模板题，必须把两条流分开画：
方向已知推出
乙 → 甲seq=1913，载荷 100B覆盖 1913 ～ 2012 ⟹ 甲下一个期望 2013 ⟹ 甲的 ack ＝ 2013
甲 → 乙乙的 ack=2046乙期望甲从 2046 开始发 ⟹ 甲的 seq ＝ 2046
⭐⭐ 两条交叉规则（本题的全部内容）：
我的 seq  ＝ 对方刚发来的 ack       （对方期望我从这里开始）
我的 ack  ＝ 对方的 seq ＋ 对方的载荷 （我收全到哪儿了，就期望下一个）
⚠️⚠️ 四个选项就是两个 ±1 的全排列，逐个溯源：
选项seqack错法
A2046 ✅2012ack 忘了 +1（2012 是末字节，不是下一个）
B2046 ✅2013 ✅—
C20472012两处都错
D20472013 ✅seq 多加了 1——把「对方的 ack」又往后挪了一格
📌 D 是最强干扰项：很多人下意识觉得「两个数都该 +1」。实际上 seq 直接照抄对方的 ack（一个字都不改），只有 ack 才需要「载荷末尾 +1」。
2011實戰第二次握手的合法字段
主机甲向主机乙发送一个（SYN=1, seq=11220）的 TCP 段，期望与主机乙建立 TCP 连接，若主机乙接受该连接请求，则主机乙向主机甲发送的正确的 TCP 段可能是（　）。

在 TCP 三次握手中，当主机乙接受连接请求时，必须发送 SYN=1 且 ACK=1 的报文段。确认序号 ack 应为甲初始序号 seq=11220 加 1，即 11221。乙的序号 seq 由其自行选择，与甲的序号无关，可为任意值。因此选项 C（SYN=1, ACK=1, seq=11221, ack=11221）符合要求。
第二次：SYN=1,ACK=1，ack=x+1=11221；seq 是乙自己选的。
再深一层
选 C。本题只考两个判据，两刀就能砍到答案：
刀一：第二次握手必须 SYN＝1 且 ACK＝1  ⟹ 砍掉 A、D
刀二：ack ＝ 甲的 seq ＋ 1 ＝ 11221       ⟹ 砍掉 B（它写了 11220）
剩下 C
⭐⭐ 题干「可能是」三个字是本题的灵魂：乙的 seq 由乙自行选择，与甲的 11220 毫无关系，可以是任意值——C 里的 seq 恰好也是 11221 纯属巧合，不是算出来的。所以本题只能问「可能是」，不能问「一定是」。
⚠️ 很多人在这里想歪：看到 C 的 seq 和 ack 都是 11221，以为其中有什么关系而不敢选。正确的思路是：seq 那一栏根本不用看（任何值都合法），只验 SYN/ACK 标志位和 ack 值。
📌 为什么初始序号必须随机而不能固定（5.4 疑难点第 5 条）：防止网络中滞留的旧报文段落进新连接的窗口内被误收。所以 TCP 采用「随时间递增的随机化初始序号」——这正是「乙的 seq 可为任意值」的根源。
2019實戰第三次握手的确认序号
若主机甲主动发起一个与主机乙的 TCP 连接，甲、乙选择的初始序号分别为 2018 和 2046，则第三次握手 TCP 段的确认序号是（　）。

三次握手过程：甲发 SYN(seq=2018)；乙回 SYN+ACK(seq=2046, ack=2019)；甲再发 ACK。第三次握手的确认序号应为乙的初始序号加 1，即 2046+1 = 2047。
第三次的 ack = 2046+1。
再深一层
选 D。本题的胜负手是「第三次握手确认的是谁的序号」。
第 1 次 甲→乙：SYN＝1，seq＝2018
第 2 次 乙→甲：SYN＝1，ACK＝1，seq＝2046，ack＝2018＋1＝2019
第 3 次 甲→乙：ACK＝1，seq＝2019，ack＝2046＋1＝2047  ← 问的是这个
⚠️⚠️ 四个选项两两配对，把两个方向的确认号都摆出来让你选错：
选项它是什么
A 2018甲的初始序号本身
B 2019第二次握手的确认号（乙确认甲）—— 最强干扰项
C 2046乙的初始序号本身
D 2047第三次握手的确认号（甲确认乙）✅
⭐ 一句话判据：「确认号 = 对方序号 + 1」，问第几次握手，就看这一次是谁在确认谁。第二次是乙确认甲 ⟹ 用甲的 2018；第三次是甲确认乙 ⟹ 用乙的 2046。
📌 做这类题的稳妥办法：把三行字段表完整写出来再读题，写全比心算快，也不会认错方向。
做完再翻：这些题到底在问什么

序号确认题有三种：连续发几段，ack 是多少；中间丢了一段，ack 停在哪；双方互相发时自己的 seq 等于对方的 ack。全部只用 ack = 下一个期望字节。 握手题：SYN 占一个序号，所以第三次的 seq 是 x+1。 UDP 分用只用目的端口。
