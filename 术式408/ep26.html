其之壹三级调度

调度发生在三个层面，从慢到快：

  • 高级调度（作业调度）：外存后备队列 → 内存，一个作业只调入一次。
  • 中级调度（内存调度）：内存不够时把进程换到外存（挂起），之后再换回。
  • 低级调度（进程调度）：就绪 → 运行。最频繁，每几十毫秒一次。

这一话说的调度，默认指最后一种。

术式
衡量好坏的指标

周转时间 = 完成时间 − 到达时间。
带权周转时间 = 周转时间 ÷ 服务时间（≥1）。
等待时间 = 周转 − 服务（I/O 不计入等待时，还要减）。
响应时间 = 首次得到 CPU − 到达。
CPU 利用率 = 忙 ÷ 总。吞吐量 = 完成数 ÷ 时间。

带权周转把「等了多久」和「活有多长」放在一起看。同样等 10 分钟，1 分钟的活和 100 分钟的活感受完全不同。

其之貳调度的时机和方式

调度时机分两类：

术式
什么时候能调度

要调度：当前进程结束、阻塞；时间片用完；有更高优先级进程到达（抢占）。
不能调度：正在处理中断；执行原语；进程在内核程序的临界区中。
普通临界区可以调度：进程在用户程序的临界区（比如正在用打印机）时可以被抢占，只是别人进不了这个临界区。

内核临界区不能切，因为它保护的是调度器自己要用的数据（比如就绪队列），切走会乱。打印机这种临界区要占用很久，如果不让调度，CPU 就白等了。

非抢占式：除非进程自己放弃，否则一直运行。抢占式：新来的更紧急就立刻换。

闲逛进程：就绪队列为空时运行它。优先级最低，只要有别的进程就绪就让出，不占资源，也可以让 CPU 降低功耗。它保证了 CPU 永远有事可做，调度器不用特判。

术式
上下文切换

调度是选一个；切换是实施。
切换内容：保存 PC、PSW、通用寄存器到 PCB；更新 PCB 状态并放入队列；选中新进程，加载它的现场；切换地址空间（页表基址），TLB 随之作废。
切换本身不做有用功，还让 TLB 和 Cache 失效。同一进程内的线程切换不用换地址空间，开销小得多。

调度程序（scheduler） 由排队器、分派器、上下文切换器组成。排队器把就绪进程排好，分派器把选中的进程放上 CPU。

合上页面说一遍：为什么内核临界区不能调度，普通临界区可以？切换比线程切换多了什么？

内核临界区保护调度器自己要用的数据，普通临界区只是别人进不来。进程切换还要换页表、作废 TLB。

咒灵
SJF 和 SRTN 的问题

服务时间要预估，用户可能乱报。长作业可能饥饿：短作业一直来，长作业永远轮不到。 SJF 只有在所有进程同时到达时才保证平均周转最短；考虑不同时到达时，SRTN 才是真正的最优。

HRRN 高响应比优先

怎么既偏向短作业，又让长作业等久了能轮到？把等待时间算进去。

优先级与多级反馈

优先级调度：可以抢占或非抢占；优先级可以静态（不变，可能饥饿）或动态（等久了提高，防饥饿）。

排序的常识：系统进程高于用户进程，交互型高于批处理，I/O 型高于 CPU 型。原因是 I/O 型用一会儿 CPU 就去等 I/O 了，先让它用，既不占 CPU 多久，又让设备保持忙碌。

多级反馈队列：多个队列，优先级从高到低，时间片从短到长。

  1. 新进程进第 1 级队列。
  2. 用完时间片还没结束，掉到下一级。
  3. 只有上一级队列空了，才运行下一级。
  4. 高优先级来人时抢占，被抢的放回本级队尾。

这样短作业和 I/O 型在高层很快完成，长作业沉到底层，一次能跑很久。它不用事先知道服务时间，最全面；但如果一直有新进程来，底层的可能饥饿。

带 I/O 的情况

进程不是一直占着 CPU。遇到 I/O 就阻塞，CPU 转给别人，I/O 和 CPU 可以同时进行。这种情况要画两条时间线：一条 CPU、一条设备。

例：P1 计算 10 → I/O 20 → 计算 10；P2 计算 30。P1 先跑。0–10 P1 算；10–30 P1 在 I/O，CPU 给 P2；30 时 P1 回来了，非抢占的话 P2 接着跑到 40，P1 在 40–50 算完。总用时 50，CPU 没有闲过。如果两者串行要 70。这就是多道程序的好处。

其之肆多处理机和线程调度

用户级线程的调度：操作系统只调度进程，进程内部线程由线程库决定。同一进程的线程切换不进内核。

内核级线程的调度：操作系统直接调度线程。如果切换的两个线程属于不同进程，就要切地址空间；同属一个进程就不用。

多处理机调度有两种：

  • 公共就绪队列：所有 CPU 从同一个队列取。天然负载均衡，但访问要互斥，而且进程容易换 CPU。
  • 私有就绪队列：每个 CPU 自己一个队列。进程留在原来的 CPU 上，处理机亲和性好（Cache 里还有它的数据）。但要主动做负载均衡：把忙的 CPU 上的进程迁到闲的 CPU（push 或 pull）。
领域展开

指标：周转 = 完成 − 到达；带权 = 周转 ÷ 服务。
算法：SRTN 周转最优、HRRN 折中不饥饿、RR 响应快、多级反馈最全面。
不能调度：中断处理、原语、内核临界区。
切换代价：进程切换要换页表，线程不用。

2009實戰高响应比优先
下列进程调度算法中，综合考虑进程等待时间和执行时间的是（　）。

响应比 = (等待时间 + 执行时间)/执行时间。它综合考虑了每个进程的等待时间和执行时间，对于同时到达的长进程和短进程，短进程会优先执行，以提高系统吞吐量；而长进程的响应比可以随等待时间的增加而提高，不会产生进程无法调度的情况。
再深一层
选 D。题干里「等待时间 + 执行时间」这七个字，就是响应比公式的分子，几乎是明送。
四个算法各自「看什么」：
  A RR   ：只看队列位置（谁都不看）
  B SJF  ：只看执行时间
  C FCFS ：只看到达时刻
  D HRRN ：R = (等待 + 执行)/执行 ⟹ 两个都看 ✓
⭐ HRRN 是 SJF 与 FCFS 的「折中产物」，这个定位要牢记：服务时间在分母 ⟹ 继承了 SJF 偏向短作业；等待时间在分子 ⟹ 继承了 FCFS 的公平性。2011 真题（2.2-39）正是问「谁同时具备这两点」，答案还是它。

2011實戰高响应比优先不会饥饿
下列选项中，满足短作业优先且不会发生饥饿现象的是（　）调度算法。

响应比 = (等待时间 + 执行时间)/执行时间。在等待时间相同的情况下，作业执行时间越短，响应比越高，满足短任务优先；随着长作业等待时间的增加，响应比会变大，执行机会也会增大，因此不会发生饥饿现象。先来先服务和时间片轮转不符合短任务优先，非抢占式短作业优先会产生饥饿现象。

⚠️ D 的「非抢占」是烟雾弹：不少人以为非抢占就不会饥饿。错——只要新到的短作业源源不断，长作业在每个调度点都排最后，2014 真题（2.2-43）把抢占与非抢占 SJF 两个选项并列，两个都判为「会饥饿」。
2013實戰I/O 型进程优先级更高
某系统正在执行三个进程 P₁、P₂ 和 P₃，各进程的计算（CPU）时间和 I/O 时间比例如下表所示。为提高系统资源利用率，合理的进程优先级设置应为（　）。
进程计算时间I/O 时间
P₁90%10%
P₂50%50%
P₃15%85%

为了合理地设置进程优先级，应综合考虑进程的 CPU 时间和 I/O 时间。一般来说，I/O 型作业的优先权高于计算型作业的优先权，这是由于 I/O 操作需要及时完成，它没有办法长时间地保存所要输入/输出的数据，所以考虑到系统资源利用率，要选择 I/O 繁忙型作业有更高的优先级。
I/O 比例越大的优先级越高。
再深一层
选 B。「I/O 型优先」这条规则的理由比结论更该记，因为大题会让你解释：
让 I/O 型进程（P₃，85% 时间在做 I/O）先跑：
  它只用一小会儿 CPU，就去启动外设、然后阻塞
  ⟹ CPU 立刻空出来给计算型的 P₁ 用
  ⟹ 此刻：外设在忙 + CPU 也在忙 ⟹ 两种资源同时利用

反过来让计算型 P₁ 先跑：
  它一占 CPU 就是很久，P₃ 干等
  ⟹ 这段时间外设全空闲 ⟹ 只有 CPU 在忙 ⟹ 利用率低
📌 一句话答题模板：「优先调度 I/O 型进程，可使其尽早启动外设，从而让 CPU 与 I/O 设备并行工作，提高系统资源利用率。」这句话在综合题里就是采分点。
⭐ 三年一条线：2010（2.2-38，刚完成 I/O 要提优先级）→ 2013（本题，I/O 型优先级更高）→ 2016 综合题（综 10，把它写成动态优先数公式）——王道把这条规则拆成三道题考了三次。
2010實戰优先级的调整方向
下列选项中，降低进程优先级的合理时机是（　）。

选项 A 中进程时间片用完，可降低其优先级以让其他进程被调度进入执行状态。选项 B 中进程刚完成 I/O，进入就绪队列等待被 CPU 调度，为了让其尽快处理 I/O 结果，因此应提高优先级。选项 C 中进程长期处于就绪队列，为不至于产生饥饿现象，也应适当提高优先级。选项 D 中进程的优先级不应该在此时降低，而应在时间片用完后再降低。
时间片用完了，说明它是 CPU 型，降低它。
再深一层
选 A。四个选项恰好把「什么时候升、什么时候降」全考了一遍：
时机该怎么调理由
A 时间片用完降 ✓说明它是 CPU 密集型，占用够久了
B 刚完成 I/O 进就绪升I/O 型进程，让它快点处理完再去用外设

📌 底层就一条原则（2.2-22 的口径）：「占用 CPU 越多 ⟹ 优先级越低；等待越久 ⟹ 优先级越高」。A 是前半句，B、C 是后半句。
⭐ D 的措辞很微妙：书答说「应在时间片用完后再降」——差别是「刚开始跑」与「跑满一片」。降优先级要有依据（真的占用了 CPU），不能凭意图。
🔗 这就是多级反馈队列的降级规则（时间片用完才降一级），也是 2016 综合真题（综 10）里 k₁·cpuTime 那一项的现实含义。
2014實戰哪些调度算法会饥饿
下列调度算法中，不可能导致饥饿现象的是（　）。

采用静态优先级调度且系统总是出现优先级高的任务时，优先级低的任务总是得不到 CPU 而产生饥饿现象；而短任务优先调度不管是抢占式还是非抢占的，当系统总是出现新来的短任务时，长任务会总是得不到 CPU，产生饥饿现象。因此选项 B、C、D 都错误。
再深一层
选 A。本题把 SJF 拆成抢占与非抢占两项并列，摆明了要告诉你：两个都会饿。
饥饿的判据（2.2-35 那条）：排序依据会不会随「等待」而改善？
  A 时间片轮转 ⟹ 一圈必轮到，等待时间有上界 (n−1)q ⟹ 绝不饥饿 ✓
  B 静态优先数 ⟹ 优先级定死，低的永远低 ⟹ 饿
  C 非抢占 SJF ⟹ 每个调度点长任务都排最后 ⟹ 饿
  D 抢占 SRTN ⟹ 不但排最后，跑一半还会被夺 ⟹ 饿得更快
📌 「静态」两个字是 B 的死穴：若改成动态优先数（带老化），就不会饿了——2016 综合真题（综 10）第 1 问问的正是「为什么 priority = nice 会饥饿」，第 2 问要你加上 −k₂·waitTime 这一项把它救回来。
⚠️ RR「绝不饥饿」的严格表述：等待时间有确定的上界（不超过一圈）。注意这不等于「效率高」——RR 的平均周转时间通常比 SJF 差得多（2.2-27 里 RR 是四个算法中最差的）。公平与高效是两回事。
2019實戰二级反馈队列与平均等待时间
系统采用二级反馈队列调度算法进行进程调度。就绪队列 Q₁ 采用时间片轮转调度算法，时间片为 10ms；就绪队列 Q₂ 采用短进程优先调度算法；系统优先调度 Q₁ 队列中的进程，当 Q₁ 为空时系统才会调度 Q₂ 中的进程；新创建的进程首先进入 Q₁；Q₁ 中的进程执行一个时间片后，若未结束，则转入 Q₂。若当前 Q₁、Q₂ 为空，系统依次创建进程 P₁、P₂ 后即开始进程调度，P₁、P₂ 需要的 CPU 时间分别为 30ms 和 20ms，则进程 P₁、P₂ 在系统中的平均等待时间为（　）。

P₁ 和 P₂ 依次创建后进入队列 Q₁，根据时间片调度算法的规则，P₁ 和 P₂ 将依次被分配 10ms 的 CPU 时间，两个进程分别执行完一个时间片后都会被转入队列 Q₂。就绪队列 Q₂ 采用短进程优先调度算法，此时 P₁ 还需要 20ms，P₂ 还需要 10ms，所以 P₂ 会被优先调度执行，10ms 后 P₂ 执行完成，之后 P₁ 再调度执行，再过 20ms 后 P₁ 也执行完成。等待时间：P₁ = 20ms、P₂ = 10ms，平均 = 15ms。
P₁、P₂ 各跑一个 10ms 时间片后都进 Q₂；Q₂ 里短的优先，P₂ 还需 10ms 先跑，P₁ 再跑 20ms。等待时间 P₁=20、P₂=10，平均 15ms。
再深一层
选 C。🐍 Python 复算 = 15ms ✓。⚠️ 本题问的是「平均等待时间」不是周转时间——这是最大的坑。
完整时间轴：
   0–10   P₁ 在 Q₁ 跑一片（剩 20）⟹ 转入 Q₂
  10–20   P₂ 在 Q₁ 跑一片（剩 10）⟹ 转入 Q₂
  20–30   Q₁ 空 ⟹ 调 Q₂，SPF 剩 P₂(10) < P₁(20) ⟹ P₂ 完成于 30
  30–50   P₁ 跑完剩余 20 ⟹ P₁ 完成于 50

等待时间 = 在就绪队列里干等（没占 CPU）的时长：
  P₁：10–30 这 20ms 在等（0–10 和 30–50 都在跑）⟹ 20ms
  P₂：0–10 这 10ms 在等（10–20 和 20–30 都在跑）⟹ 10ms
  平均 = (20+10)/2 = 15ms

（若问周转时间：P₁ = 50、P₂ = 30，平均 40 —— 那才是干扰项的来源）
📌 等待时间的算法有个捷径：等待时间 = 周转时间 − 实际运行时间。P₁：50 − 30 = 20 ✓；P₂：30 − 20 = 10 ✓。比逐段数区间快得多。
⚠️ Q₂ 用 SPF 时比的是「还需要多少」不是「原本要多少」：此刻 P₁ 剩 20、P₂ 剩 10 ⟹ P₂ 先。若按原始需求（30 vs 20）比，顺序倒是一样，但遇到别的数据就会错。

2016實戰三种独占设备的流水排程
某单 CPU 系统中有输入和输出设备各 1 台，现有 3 个并发执行的作业，每个作业的输入、计算和输出时间均分别为 2ms、3ms 和 4ms，且都按输入、计算和输出的顺序执行，则执行完 3 个作业需要的时间最少是（　）。

这类调度题目最好画图。因 CPU、输入设备、输出设备都只有一个，因此各操作步骤不能重叠，画出运行时的甘特图后，就能清楚地看到不同作业间的时序关系，最少需要 17ms。
三个进程共用一台输入和一台输出，画时间线：3 个输入 + 3 个计算 + 3 个输出的流水。
再深一层
选 B。🐍 Python 排程复算 = 17ms ✓。这是一道典型的「三工位流水线」题：
作业输入（各 2ms）计算（各 3ms）输出（各 4ms）
10–22–55–9
22–45–89–13
34–68–1113–17

2016實戰静态优先数导致饥饿 · 动态优先数的设计
某个进程调度程序采用基于优先数（priority）的调度策略，即选择优先数最小的进程运行，进程创建时由用户指定一个 nice 作为静态优先数。为了动态调整优先数，引入运行时间 cpuTime 和等待时间 waitTime，初值均为 0。进程处于运行态时，cpuTime 定时加 1，且 waitTime 置 0；进程处于就绪态时，cpuTime 置 0，waitTime 定时加 1。请回答下列问题：
1）若调度程序只将 nice 的值作为进程的优先数，即 priority = nice，则可能出现饥饿现象。为什么？
2）使用 nice、cpuTime 和 waitTime 设计一种动态优先数计算方法，以避免产生饥饿现象，并说明 waitTime 的作用。
解：
1）因为采用了静态优先数，当就绪队列中总有优先数较小的进程时，优先数较大的进程一直没有机会运行，所以会出现饥饿现象。
2）一种动态优先数计算方法为：
priority = nice + k₁×cpuTime − k₂×waitTime  （k₁, k₂ > 0）
其中 k₁、k₂ 分别用来调整 cpuTime 和 waitTime 在 priority 中所占的比例。若一个进程的运行时间较长，则其 cpuTime 就增加，进而降低其优先级；若一个进程的等待时间较长，则其 waitTime 增加，进而会提高其优先级。于是，waitTime 就可使长时间等待的进程优先数减少，进而避免出现饥饿现象。
第 1 问：静态优先数会饥饿。第 2 问：priority = nice + k₁×cpuTime − k₂×waitTime（优先数越小越优先），运行久了优先级降、等久了优先级升。这个公式就是考点。
再深一层
一致。⭐ 本题是 2.2 唯一一道综合真题，也是「动态优先级」这条主线的终点——它把 2010、2013 两年选择题的结论写成了公式。
priority = nice + k₁·cpuTime − k₂·waitTime    （k₁, k₂ > 0）
           ↑静态基准  ↑惩罚占 CPU 久的   ↑补偿等得久的
              （SJF 的味道）      （老化 aging，防饥饿）

符号方向的验算（本题优先数越小越优先）：
  跑得久 ⟹ cpuTime↑ ⟹ priority↑ ⟹ 越不优先 ✓
  等得久 ⟹ waitTime↑ ⟹ priority↓ ⟹ 越优先   ✓
⚠️ 符号写反是本题最主要的失分方式。务必先确认题干是「优先数小者优先」还是「优先级高者优先」——本题说的是优先数（priority 值小 = 优先），所以 waitTime 前面是减号。若题目改成「优先级高者优先」，两个符号都要反过来。
📌 第 1 问的标准答法（两句，缺一不可）：① priority = nice 是静态的，进程一旦创建就不再改变；② 只要就绪队列中持续有优先数更小的进程到达，优先数大的进程永远排不到，即产生饥饿。
⭐ waitTime 的作用要单独点出来（题干专门问了）：它是唯一能随时间自动改善某个进程处境的项——没有它，公式就退化成「静态优先 + 惩罚」，长进程照样可能饿死。
🔗 本题与高响应比优先是同一个思想的两种写法：HRRN 的 R = 1 + 等待/服务，把等待放在分子；本题把 waitTime 放在减号后面——都是「让等待时间参与排序」，这就是所有防饥饿机制的共同内核。答题时若能补一句「这与高响应比优先算法的思想一致」，是加分的。
做完再翻：这些题到底在问什么

算法特征题只问三件事：抢不抢占、会不会饥饿、照顾谁。
计算题的陷阱都在时间线上：系统何时开始调度（不一定是 0 时刻）、调度和切换有没有额外开销、I/O 期间 CPU 让给谁。遇到带 I/O 的题，别心算，画两条时间线。
