其之壹问题：x++ 不是一步

x++ 在机器上是三步：读 → 加 → 写（第 20 话见过）。中断可以发生在任意两条指令之间。两个线程交错执行：

▣ 为什么要互斥
thread1thread2内存 x
t1mov eax,[x] (eax=0)0
thread1 读到 0。
thread1thread2内存 x
t1mov eax,[x] (eax=0)0
t2mov eax,[x] (eax=0)0
切换。thread2 也读到 0。
thread1thread2内存 x
t1mov eax,[x] (eax=0)0
t2mov eax,[x] (eax=0)0
t3add, mov [x],eax1
thread2 写回 1。
thread1thread2内存 x
t1mov eax,[x] (eax=0)0
t2mov eax,[x] (eax=0)0
t3add, mov [x],eax1
t4add, mov [x],eax1
thread1 也写回 1。加了两次，x 只变成 1。

结果取决于谁先谁后，这叫竞争条件。解决办法是：这三步要么全做，要么一步不做，中间不许别人碰 x。

术式
基本概念

临界资源：一次只能一个进程用（打印机、共享变量）。临界区：访问临界资源的那段代码。
互斥：不能同时用。同步：有先后，A 做完 B 才能做。
一个进程的结构：进入区 → 临界区 → 退出区 → 剩余区。

术式
互斥的四条准则

① 空闲让进：临界区没人，要进的可以马上进。
② 忙则等待：有人在里面，其他人等。
③ 有限等待：不能无限等（不饥饿）。
④ 让权等待：进不去就让出 CPU，不要占着 CPU 空转。
前三条必须满足；第四条尽量满足，下面可以看到很多方法做不到。

其之貳软件方法

只用共享变量来实现互斥。先看三个有缺陷的，每个失败的方式都不同：

算法做法问题
单标志 turnturn 指向谁，谁能进；出来时交给对方必须严格交替：对方不想进时，我也进不了。违反空闲让进
双标志先检查先看对方 flag，再把自己的 flag 置位两人同时看到对方没进，都进去了。违反忙则等待
双标志后检查先把自己的 flag 置位，再看对方两人都置位后都看到对方想进，谁也进不去。违反空闲让进和有限等待
Petersonflag 表意愿 + turn 谦让满足前三条，不满足让权等待

问题都出在「看」和「改」是两步。Peterson 算法的绝招是加一个「谦让」：

Peterson 算法（进程 i，另一方 j）
flag[i] = true;              // 我想进
turn = j;                    // 让你先
while (flag[j] && turn == j);  // 对方想进且轮到对方，我就等
/* 临界区 */
flag[i] = false;
比方

走廊让路

两人都想过，都说「我想过，不过你先」。turn 只有一个值，最后说的那个人说的话算数，他就让到底，另一个人先走。所以只有一个人等。

为什么它是对的：两人同时走到 while 时，turn 只能是其中一个，所以只有一个人会被挡住（互斥）；对方不想进时 flag[j]=false，我马上能进（空闲让进）；对方出来后再想进时会把 turn 给我，我不会一直等（有限等待）。while 循环一直占着 CPU，所以不满足让权等待。

其之參硬件方法

既然「看」和「改」分两步是祸根，就让硬件一步做完。

术式
三种硬件方法

关中断：进入临界区前关中断，就不会被切走。只适合单处理机内核：多核时别的 CPU 不受影响，交给用户又太危险。
TestAndSet（TSL）：原子地「读旧值、置 1」。
Swap：原子地交换两个值。
共性：后两者实现简单、适合多处理器；都忙等，不满足让权等待；可能饥饿。

TSL 实现互斥
while (TSL(&lock));   // 返回旧值：旧值 true 表示已被占
/* 临界区 */
lock = false;
Swap 实现互斥（key 是每个线程自己的局部变量）
bool key = true;
while (key) Swap(&lock, &key);   // 换出来是 false 才说明之前没人占
/* 临界区 */
lock = false;

互斥锁（自旋锁）就是用这种原子指令做的：acquire 等到锁可用就占上，release 放开。等待时一直循环，所以叫自旋。

因果

自旋并不总是坏事

单处理器上自旋纯属浪费，因为持锁者不下 CPU 就放不了锁。多处理器且临界区很短时，自旋比阻塞还便宜：省掉一次进程切换的代价。

合上页面说一遍：四条准则是什么？Peterson、TSL、关中断各满足哪些？

空闲让进、忙则等待、有限等待、让权等待。Peterson 满足前三条，TSL 满足前两条（可能饥饿），都不让权。关中断只用于单处理机内核。

其之肆信号量

前面的办法都在忙等。想让进不去的进程去睡觉，就要操作系统介入：提供一个数据结构，和两个原子操作。

记录型信号量
typedef struct {
    int value;
    struct process *L;   // 阻塞队列
} semaphore;

void wait(semaphore S) {    // P
    S.value--;
    if (S.value < 0) block(S.L);    // 申请不到就阻塞：让权等待
}
void signal(semaphore S) {  // V
    S.value++;
    if (S.value <= 0) wakeup(S.L);  // 还有人在等就唤醒一个
}

更早的整型信号量只有一个整数，while (S<=0); 还是忙等。这里的记录型信号量才解决了让权等待。

术式
信号量的语义

value > 0：还有这么多可用资源。value < 0：有 |value| 个进程在等。
初值：互斥 = 1；同步 = 0；资源 = 数量。
P、V 本身是原语，靠关中断或 TSL 实现，时间极短。

P、V 自己的原子性怎么保证：单处理机用开关中断。但整型信号量 while (S<=0); 不能把整个循环放在关中断里：一直关着中断，就不会切到别的进程去做 V，这个循环永远出不来。要么在循环体内开一下中断，要么用记录型信号量把进程阻塞。

算一遍：信号量初值 3，当前值 −2。说明 3 个资源都被占了，还有 2 个进程在等。

三种用法：

  • 互斥：同一进程内 P(mutex) 和 V(mutex) 夹住临界区。
  • 同步：A 做完 B 才能做。S=0，A 做完 V(S)，B 开始前 P(S)。P、V 在两个进程里。
  • 资源数：n 个打印机，S=n。
束缚

PV 三句诀

互斥：一个进程内成对，夹着临界区。 同步：前操作之后 V，后操作之前 P，分在两个进程里。 顺序：同步 P 在前，互斥 P 在后，否则死锁。V 的顺序无所谓。

为什么顺序有讲究，下一话用生产者消费者说明。

其之伍条件变量与管程

PV 到处写，一个顺序错了就死锁。管程把共享数据和对它的操作封装成一个模块（像一个类），任一时刻只有一个进程能在管程内执行，互斥由编译器保证，不用程序员写。

同步怎么办？比如生产者进了管程发现缓冲区满了。它不能傻等，因为它占着管程，消费者进不来。所以需要条件变量：

管程（生产者消费者）
monitor ProducerConsumer {
    condition full, empty;
    int count = 0;
    void insert(Item it) {
        if (count == N) wait(full);
        放入一项; count++;
        if (count == 1) signal(empty);
    }
    Item remove() {
        if (count == 0) wait(empty);
        取走一项; count--;
        if (count == N - 1) signal(full);
    }
}
术式
条件变量 vs 信号量

条件变量没有值，只有队列。x.wait() 阻塞自己，放开管程；x.signal() 唤醒一个，没人等就什么都不做（不累积）。
信号量有值，V 会累积，能记住「曾经 V 过」。
管程既能实现互斥，也能实现同步。

合上页面说一遍：信号量和条件变量差在哪？管程的互斥由谁保证？

信号量有值、V 累积；条件变量没有值、没人等的 signal 就丢了。互斥由管程的编译器保证。

领域展开

四准则：空闲让进、忙则等待、有限等待、让权等待。
只有信号量和管程让权等待；Peterson、TSL、Swap 都忙等。
PV：互斥一进程内成对；同步跨进程；同步 P 在前。
条件变量：没有值，signal 不累积。

2011實戰非原子的读-改-写造成的竞态
有两个并发执行的进程 P₁ 和进程 P₂，共享初值为 1 的变量 x。P₁ 对 x 加 1，P₂ 对 x 减 1。加 1 和减 1 操作的指令序列分别如下，两个操作完成后，x 的值（　）。
// 加 1 操作（P1）                 // 减 1 操作（P2）
load  R1, x   // 取 x 到 R1        load  R2, x   // 取 x 到 R2
inc   R1                          dec   R2
store x, R1   // 将 R1 存入 x      store x, R2   // 将 R2 存入 x

x 的最终值取决于最后执行 store 的是哪个进程。P₁ 可能存入 2（读到 x=1）或 1（读到 x=0）；P₂ 可能存入 0（读到 x=1）或 1（读到 x=2）。因此 x 的可能取值为 0、1、2。
三条指令的交错，结果可能是 0、1、2。同一模子。
再深一层
选 C。🐍 Python 穷举全部 20 种交错，x 的取值集合 = {0, 1, 2}，与书答完全一致 ✓
关键只有一句：x 的最终值 = 最后那条 store 写进去的值

三种结果各举一个序列：
  x = 2  P₂ 全跑完（x=0），P₁ 才 load ⟹ 不对…
        正解：P₁ load(1)、inc(2)，P₂ 跑完(x=0)，P₁ store ⟹ 2
  x = 0  对称：P₂ load(1)、dec(0)，P₁ 跑完(x=2)，P₂ store ⟹ 0
  x = 1  两者完全不交错（一前一后跑完）⟹ 1+1−1 = 1

⟹ 取值集合 {0, 1, 2}
⚠️ D 多出来的 −1 是怎么被排除的：要得到 −1，必须有人把「比 1 小 2」的值写进去——但每个进程只做一次 ±1，写进去的值最多偏离读到的值 1 个单位，而读到的值只可能是 0/1/2。−1 需要两次减法叠加，本题的 P₂ 只减一次。
⭐ 本题是 2.3-33 的机器级版本，也是 2018 真题（2.3-53）的前身：三题共用同一个内核——「x++ 不是原子操作，它是 load/改/store 三步」。只要这三步之间能插入别人的 store，结果就不确定。解法自然也是同一个：把这三步用 P(mutex)…V(mutex) 夹起来。
2018實戰数交错序列的个数
属于同一进程的两个线程 thread1 和 thread2 并发执行，共享初值为 0 的全局变量 x。thread1 和 thread2 实现对全局变量 x 加 1 的机器级代码描述如下。在所有可能的指令执行序列中，使 x 的值为 2 的序列个数是（　）。
thread1                        thread2
mov R1, x   // (x) → R1        mov R2, x   // (x) → R2
inc R1      // (R1)+1 → R1     inc R2      // (R2)+1 → R2
mov x, R1   // (R1) → x        mov x, R2   // (R2) → x

要使 x 的值为 2，必须先执行完 thread1 的三条指令再执行 thread2 的三条指令，或先执行完 thread2 再执行 thread1，共 2 种序列。任何交错都会导致某个线程读到旧值，最终 x = 1。
同样分析三步交错。
再深一层
选 B。🐍 Python 穷举全部 20 种交错：x = 2 的有 2 种，x = 1 的有 18 种 ✓
全部交错数 = C(6,3) = 20 种
  x = 2 ⟹ 2 种（thread1 整体在前 / thread2 整体在前）
  x = 1 ⟹ 18 种（只要有一点交错，就有人读到旧值 0）

为什么只有「完全不交错」才能得 2：
  想要 x=2，后写的那个线程必须读到 1
  ⟹ 它的 mov R,x 必须发生在前一个线程的 mov x,R 之后
  ⟹ 后者的三条指令全部在前者三条指令之后 ⟹ 只能是串行的两种
⚠️ 本题问「序列个数」而不是「x 的可能取值」，这是与 2011 真题（2.3-49）的唯一差别：2011 问取值集合（答 {0,1,2}），2018 问满足条件的序列条数（答 2）。同一个模型、两种问法，两年都考过——读题时先圈出「问的是什么」。
⭐ 手工数的方法（考场上不可能真去枚举 20 条）：把「x=2」翻译成「两次读写不重叠」，立刻得出只有两种串行序。凡这类题都应该从「结果反推约束」，而不是正着去穷举。
📌 再次印证：x++ 不是原子操作——它是 load / inc / store 三条指令，这是 2011、2016、2018 三年真题共同的底层考点。
2016實戰哪些操作需要互斥执行
进程 P₁ 和 P₂ 均包含并发执行的线程，部分伪代码描述如下所示。下列选项中，需要互斥执行的操作是（　）。
// 进程 P1                        // 进程 P2
  int x = 0;                       int x = 0;
  Thread1()                        Thread3()
  { int a;                         { int a;
      a = 1;  x += 1;                  a = x;  x += 3;
  }                                }
  Thread2()                        Thread4()
  { int a;                         { int b;
      a = 2;  x += 2;                  b = x;  x += 4;
  }                                }

a、b 是各线程的局部变量，不需要互斥；a = x 与 b = x 都是读操作，读读之间不需要互斥；x += 1 与 x += 3 分属两个不同进程，两个 x 是不同进程的变量，互不影响。只有 x += 1 与 x += 2 是同一进程内两个线程对同一共享变量的写操作，需要互斥。
只有访问同一进程的共享变量 x 才需要互斥。不同进程的 x 不是同一块内存。
再深一层
选 C。本题四个选项恰好是四条判据的反例集，逐条筛一遍就出来了。
选项为什么不需要互斥用的判据
A　a=1 与 a=2局部变量，各线程栈里各一份只有全局变量才可能需要互斥
B　a=x 与 b=x都是读操作读读不互斥
C　x+=1 与 x+=2同进程内两线程写同一个 x写写必须互斥 ✓
D　x+=1 与 x+=3分属两个进程，是两个不同的 x不同进程地址空间独立
⭐ D 是本题设计得最精巧的干扰项：P₁ 和 P₂ 里都写着 `int x = 0;`，看起来「同名就是同一个」——但进程之间地址空间是独立的，两个 x 毫无关系（除非显式用共享内存）。而同一进程内的多个线程共享全局变量，所以 Thread1 与 Thread2 的 x 才是同一个。这正好考了 2.1 那条主线：线程共享什么、进程私有什么。
📌 三步筛法（做任何「谁要互斥」的题都能用）：① 是全局变量吗？不是 ⟹ 出局；② 在同一个地址空间里吗？不在 ⟹ 出局；③ 至少有一方是写吗？全是读 ⟹ 出局。三关都过的那一对，才需要互斥。
🔗 2017 真题（综 22）就是这套筛法的大题版，那里还要额外做到「不多加锁」以保证并发度。
2010實戰识别 Peterson 算法
进程 P₀ 和进程 P₁ 的共享变量定义及其初值为 boolean flag[2]; int turn = 0; flag[0] = false; flag[1] = false;。若进程 P₀ 和进程 P₁ 访问临界资源的类 C 代码实现如下，则并发执行进程 P₀ 和进程 P₁ 时产生的情况是（　）。
void P0()                          void P1()
{                                  {
  while(true)                        while(true)
  {                                  {
    flag[0] = true; turn = 1;          flag[1] = true; turn = 0;
    while(flag[1] && (turn == 1));     while(flag[0] && (turn == 0));
    临界区;                            临界区;
    flag[0] = false;                   flag[1] = false;
  }                                  }
}                                  }

这段代码就是 Peterson 算法。Peterson 算法能保证互斥进入临界区，且满足有限等待，不会出现饥饿现象。
这是 Peterson。看书上解析：不会饥饿；互斥保证了。
再深一层
选 D。第一步就该认出来：这是 Peterson 算法，认出来本题就结束了。
Peterson 算法的三行特征（对照题干逐行核）：
  ① flag[i] = true   「我想进」        ✓ 题干第 1 句
  ② turn = j         「你先请」写对方  ✓ 第 2 句（turn=1 / 0）
  ③ while(flag[j] && turn == j);      ✓ 题干第 3 句

四准则的成绩单：
  空闲让进 ✓   忙则等待 ✓   有限等待 ✓（不饥饿）
  让权等待 ✗（在 while 里忙等，但本题没问这条）
⭐ 教材的类比（答题时能直接讲出来）：两人同时到门口，各说一句「你先走」，但各自只说一次；先说完的人请完对方，就等着对方请自己，然后光明正大进门。「只说一次」保证了不会像双标志后检查法那样互相死等。
⚠️ 选 C（会饥饿）的人通常是把它误认成「双标志后检查法」：那个算法确实会因互相死等而饥饿，差别就在有没有 turn 这个仲裁者。看到 turn 就该往 Peterson 想，看不到 turn 才是双标志法。
📌 本题不选「让权等待」的原因：选项里根本没问它。Peterson 确实不满足让权等待（2018 真题 2.3-55 专门考了这一点），但「不让权等待」不等于「不互斥」也不等于「会饥饿」，三件事别串。
2016實戰TSL 指令实现互斥的特点
使用 TSL（Test and Set Lock）指令实现进程互斥的伪代码如下所示。下列与该实现机制相关的叙述中，正确的是（　）。
do{
    …
    while(TSL(&lock));
    critical section;
    lock = FALSE;
    …
} while(TRUE);

使用 TSL 指令实现互斥时，等待进入临界区的进程一直在 while 循环中测试 lock，不会主动放弃 CPU，属于忙等待，因此不满足让权等待准则，也不存在阻塞态进程需要唤醒。TSL 指令本身就是原子操作，不需要在关中断状态下执行；若在关中断状态下执行且 lock 一直为 true，系统会因无法响应中断而终止。
TSL 必须是原子指令；等待时是在忙等，可以被调度，但不是让权等待。
再深一层
选 B。四个选项其实在考同一件事：TSL 是忙等，没有任何进程进入阻塞态。
TSL 方案的完整画像：
  等待方式   在 while 里反复执行 TSL（自旋）
  进程状态   全程运行态，没有阻塞态
  ⟹ A 错：既然没人阻塞，也就无人可唤醒
  ⟹ B 对：不主动放弃 CPU，正是忙等的定义
  ⟹ C 错：忙等 = 不让权等待
⭐ D 是本题最值得单独记的一条（两个理由，缺一不可）：① 没必要——TSL 本身就是原子指令，其原子性由「执行 TSL 的 CPU 锁住内存总线」保证，不需要再靠关中断；② 有害——若关着中断做自旋，而 lock 一直为 TRUE，那么时钟中断进不来、没人能抢占它、持锁进程也永远得不到 CPU 去释放锁，系统直接卡死。
🔗 「关中断 + 循环等待 = 死循环」这个坑，2021 真题（综 25）整道大题又考了一次：那题的方法 1 就是「关中断后 while(S≤0) 空转」，答案是错的；方法 2 在循环体里加了一对开/关中断才正确。两年真题咬同一个点，说明它是硬考点。
📌 顺便对比关中断法与 TSL 法：关中断只对本 CPU 有效 ⟹ 不适用于多处理器；TSL 靠锁总线 ⟹ 适用于多处理器。这是 2.3.2 节的核心分界线之一。
2010實戰信号量当前值的两个含义
设与某资源关联的信号量初值为 3，当前值为 1。若 M 表示该资源的可用个数，N 表示等待该资源的进程数，则 M、N 分别是（　）。

信号量当前值为 1，表示还有 1 个资源可用，即 M = 1。既然资源还有剩余，就不可能有进程在等待该资源，即 N = 0。
初值 3 现值 1，说明还有 1 个可用，没人等待。
再深一层
选 B。本题只需一句话：信号量为正时，绝不可能有人在等。
当前值 = 1 > 0
  ⟹ M = 1（值本身就是可用资源数）
  ⟹ N = 0（还有货，谁会去排队？）

反过来，若当前值 = −2：
  ⟹ M = 0（一个都不剩）
  ⟹ N = 2（|−2| 个在等）

M 与 N 永远不会同时为正 —— 这是本题唯一的考点。
⚠️ C（1, 2）是最毒的干扰项：它诱导你去用初值 3 减当前值 1 得「2 个被占用」，再把这 2 个说成「在等待」。被占用 ≠ 在等待——3 − 1 = 2 确实是「已被分配出去的资源数」，但那 2 个进程正在使用资源，它们跑得好好的，没有任何人被阻塞。
⭐ 把三个量分清（考场上写在草稿纸上）：初值 3 ＝ 资源总数；当前值 1 ＝ 剩余可用；初值 − 当前值 = 2 ＝ 已占用；只有当前值为负时，它的绝对值才是「等待进程数」。
🔗 与 2.3-03（初值 3、当前 −1 ⟹ 1 个等待）是同年同源的一对，两题合看就完整了。
2018實戰哪种同步机制能让权等待
在下列同步机制中，可以实现让权等待的是（　）。

Peterson 方法、swap 指令、TestAndSet 指令都采用忙等待方式，进程在等待时不会放弃 CPU，均不满足让权等待。只有信号量方法（记录型信号量）通过 block 原语使进程自我阻塞，实现了让权等待。
这是信号量相对前面所有方法的优势。
再深一层
选 C。⭐ 一句话结论：只有记录型信号量（和管程）会让权等待，其余全是忙等。
机制等待时干什么让权等待
单标志法 / 双标志法 / Peterson在 while 里空转✗
TS 指令 / Swap 指令反复执行原子指令✗
互斥锁（自旋锁）反复 acquire()✗
整型信号量while(S≤0) 空转✗ ⚠️
记录型信号量block() 自我阻塞，挂入等待队列✓
⚠️ 「整型信号量也不让权等待」是本表最容易漏的一行：本题选项写的是笼统的「信号量方法」，408 默认指记录型，但若题目明确写「整型信号量」，答案就要反过来。（教材原文：整型信号量「未遵循让权等待准则，会浪费 CPU 时间」。）
⭐ 为什么只有记录型能做到：因为它多带了一个等待队列 L——有了队列才能把进程「存起来」，才敢让它睡；没有队列，进程一睡就再也没人叫得醒它。数据结构的差别，直接决定了行为的差别。
🔗 2020 真题（2.3-56）从反面又考了一次：让权等待是四准则里唯一「不必须」的一条，正因为 Peterson 这些不让权的方法仍然是正确的互斥算法。
2018實戰条件变量的 wait 操作
若 x 是管程内的条件变量，则当进程执行 x.wait() 时所做的工作是（　）。

x.wait() 的作用是阻塞当前进程，并将其插入条件变量 x 的阻塞队列中，同时释放管程的使用权，以便其他进程能够进入管程。
再深一层
选 D。⚠️ C 是本题精心设计的陷阱：条件变量没有值，谈何「根据 x 的值判断」。
信号量 P(S)条件变量 x.wait()
有数值吗有（S.value）没有（只有队列）
会不会阻塞看情况：value≥0 就直接过无条件阻塞，一定入队
额外动作无自动释放管程 ⭐
⭐⭐ 「自动释放管程」是 x.wait() 最容易被忽略、却最关键的一步：进程是在管程内部执行时才发现条件不满足的，此时它正占着管程；若阻塞时不放手，其他进程就再也进不来，也就永远没人能让条件变成真——整个系统直接停摆。教材原话：「它必须释放对管程的占用；否则其他进程将无法进入管程，从而导致系统停滞。」
⚠️ B 说的是 x.signal()，不是 wait（一字之差，方向相反）。
🔗 与 2.3-29 合起来才是条件变量的完整图像：wait ＝ 无条件阻塞 + 释放管程；signal ＝ 唤醒一个，若没人等就什么也不做（无记忆）。
2016實戰管程既能互斥也能同步
下列关于管程的叙述中，错误的是（　）。

管程不仅能实现进程互斥（任一时刻只有一个进程能在管程内执行），还能通过条件变量实现进程同步，因此 A 错误。B、C、D 均正确。
再深一层
选 A。一个「只」字就把 A 判死了——管程的能力是互斥 加 同步。
管程的两项能力靠什么实现程序员要写吗
互斥管程本身的性质（编译器保证一次一个进程）不用写 ⭐
同步条件变量 x.wait() / x.signal()要写
⭐ 「互斥不用写、同步要写」是管程最该记住的分工：这正是管程相对信号量的卖点——把最容易写错的互斥部分自动化了，但「什么时候该等、什么时候该叫醒」这种业务逻辑仍得程序员自己表达。
📌 另外三项各对应一个考点，正好复习一遍：B ＝ 管程是编程语言的构件（Java 的 synchronized 就是管程思想的落地）；C ＝ 互斥性；D ＝ 封装性（与 2.3-28 里那个杜撰的 C 选项正好对照）。
⚠️ 做「错误的是」这类题的通用动作：找绝对化词——「只能」「一定」「必须」「所有」出现时优先怀疑。本题的 A 就栽在「只能」上。
