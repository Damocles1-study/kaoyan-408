#20
@stem
总线甲宽度为 64 位，时钟频率为 400MHz，采用 DDR 技术（每个时钟周期的上升沿、下降沿各传送一次数据）；总线乙宽度为 32 位，工作频率标为 1600MT/s。甲、乙两条总线的带宽分别是（　）。
@A 6.4GB/s，6.4GB/s
@B 3.2GB/s，6.4GB/s
@C 6.4GB/s，12.8GB/s
@D 6.4GB/s，3.2GB/s
@ans A
::read
「时钟频率 400MHz」「每个时钟周期……各传送一次」 >> 时钟频率要乘每周期传送次数 2
「工作频率标为 1600MT/s」 >> MT/s 就是每秒传送多少百万次，已经是传送率，不能再乘
::fast
{{秒|甲 8B×800M，乙 4B×1600M}}，都是 6.4GB/s ⟹ A。
::steps
甲：每秒传送 $400\text{M}\times2=800\text{M}$ 次，每次 8B ⟹ $6.4$GB/s。
乙：每秒传送 1600M 次，每次 4B ⟹ $6.4$GB/s，选 **A**。
::note
- 干扰项来路：B 是甲忘了 DDR 乘 2；C 是把 MT/s 当时钟频率又乘了 2；D 是乙按 800MHz 算。
- 2024、2025 两年真题正反各考一次：给「时钟频率」要乘，给「MT/s」不乘。
::

#28
@stem
某系统用伙伴系统管理 1MB 的内存（起始地址为 0），开始时整个内存是一个空闲块。依次申请 A ＝ 70KB、B ＝ 35KB、C ＝ 80KB，然后释放 A。此时空闲块的个数是（　）。
@A 2
@B 3
@C 4
@D 5
@ans C
::read
「伙伴系统」 >> 申请按 2 的幂向上取整，大块一半一半劈；回收只和同样大小、互为伙伴的空闲块合并
::fast
{{秒|A 的伙伴被劈开给了 B}}：A 释放时无伙伴可并，空闲块是 128K、64K、128K、512K 共 4 个 ⟹ C。
::steps
A 需 128K：1024 劈成 512＋512，再劈 256＋256，再劈 128＋128，A 占 [0,128K)；空闲 128K@128K、256K@256K、512K@512K。
B 需 64K：把 128K@128K 劈成两个 64K，B 占 [128K,192K)；空闲 64K@192K、256K@256K、512K@512K。
C 需 128K：把 256K@256K 劈开，C 占 [256K,384K)；空闲 64K@192K、128K@384K、512K@512K。
释放 A（128K@0）：它的伙伴是 [128K,256K) 这一块，已被劈开且 B 在用 ⟹ 不能合并。
空闲块：128K@0、64K@192K、128K@384K、512K@512K，共 4 个，选 **C**。
::note
- 伙伴地址 ＝ 本块地址 ⊕ 本块大小：128K@0 的伙伴是 128K@128K。地址相邻但大小不同（如 64K@192K）不能合并。
- 3 ＝ 误把 A 与相邻的 64K 合并；2 ＝ 误以为 A 释放后一路合并回去。
::

#35
@stem
在采用 CSMA/CA 的 802.11 无线局域网中，数据传输速率为 54Mb/s，SIFS ＝ 10μs，DIFS ＝ 50μs。站 A 使用 RTS/CTS 机制向站 B 发送一个长度为 1350B 的数据帧，RTS、CTS、ACK 帧的发送时延分别为 20μs、15μs、15μs，忽略传播时延。RTS 帧中持续时间（NAV）字段的值至少应为（　）。
@A 235μs
@B 260μs
@C 280μs
@D 310μs
@ans B
::read
「RTS 帧中」的 NAV >> 从 RTS 发完开始，要预约到 ACK 结束：SIFS → CTS → SIFS → 数据 → SIFS → ACK
「1350B」「54Mb/s」 >> 数据帧发送时延 $1350\times8/54\text{M}=200$μs
::fast
{{秒|三个 SIFS ＋ CTS ＋ 数据 ＋ ACK}}：$30+15+200+15=260$μs ⟹ B。
::steps
数据帧发送时延 $1350\times8\div(54\times10^6)=200$μs。
RTS 里的 NAV ＝ SIFS ＋ CTS ＋ SIFS ＋ 数据 ＋ SIFS ＋ ACK ＝ $10+15+10+200+10+15=260$μs，选 **B**。
::note
- 235μs 是 CTS 帧里的 NAV（从 CTS 发完算起，少了 SIFS ＋ CTS）；280μs 把 RTS 自己的 20μs 也算进去；310μs 再加了 DIFS。
- DIFS 只在发 RTS 之前等，不在预约期内。
::

#41
::think
1. 宽度 ＝ 结点最多的那一层的结点数 ⟹ 层序遍历，按层计数。
2. 怎么知道一层结束了：用 last 记下「本层最后一个结点入队后的队尾位置」，出队指针走到 last 时本层结束，更新最大值，last 跳到当前队尾。
3. 每个结点进出队一次 ⟹ $O(n)$ 时间，队列 $O(n)$ 空间。
::paper
解　(1) 基本设计思想 ⛳4
采用层次遍历。用队列保存结点，变量 last 指向当前层最后一个结点在队列中的下一个位置，cnt 记录当前层已出队的结点数。每出队一个结点就把它的孩子入队、cnt 加 1；当出队指针 front 等于 last 时，说明本层结点已全部出队，用 cnt 更新最大宽度，cnt 清零，last 更新为当前队尾 rear。
(2) 算法实现 ⛳7
```
#define MaxSize 100
typedef struct BiTNode { int data; struct BiTNode *lchild, *rchild; } BiTNode, *BiTree;
int Width(BiTree b){
    BiTree Q[MaxSize];
    int front = 0, rear = 0, last = 1, cnt = 0, max = 0;
    Q[rear++] = b;                       // 根入队，第一层只有它
    while (front < rear) {
        BiTree p = Q[front++];
        cnt++;
        if (p->lchild) Q[rear++] = p->lchild;
        if (p->rchild) Q[rear++] = p->rchild;
        if (front == last) {             // 本层全部出队
            if (cnt > max) max = cnt;
            cnt = 0;
            last = rear;                 // 下一层的结束位置
        }
    }
    return max;
}
```
(3) 时间复杂度 $O(n)$，空间复杂度 $O(n)$。⛳2
::note
- 也可以给每个结点记层号（队列里存 (结点, 层号)），遍历完再统计每层结点数，书上就是这种写法，同样满分。
- 递归求每层结点数（先序遍历带层号，数组 cnt[层号]++）也对，空间是 $O(h)$ ＋ 计数数组。
- {{扣|队列溢出}}：非环形队列要开到结点数那么大；题目说非空树，不必判空。
- 代码已与「递归按层计数」对拍 20 万棵随机二叉树（`_build/mock/chk/width.c`）。
::

#42
::think
1. k 路最佳归并树 ＝ k 叉哈夫曼树：每次选最小的 k 个合并。
2. 先判要不要补虚段：$(n-1)\bmod(k-1)=11\bmod3=2\ne0$ ⟹ 补 $k-1-2=1$ 个长度为 0 的虚段。
3. WPL ＝ 所有合并结果之和（也 ＝ 各叶子 × 深度之和），它就是归并时的读写记录数的一半。
::paper
解　$n=12$，$k=4$，$(n-1)\bmod(k-1)=2\ne0$，需补 $(k-1)-2=1$ 个长度为 0 的虚段。⛳2
叶子按长度排序：0, 3, 6, 8, 9, 18, 20, 30, 44, 60, 62, 68, 85。⛳1
逐次取最小的 4 个合并：⛳4
1. 0 ＋ 3 ＋ 6 ＋ 8 ＝ 17
2. 9 ＋ 17 ＋ 18 ＋ 20 ＝ 64
3. 30 ＋ 44 ＋ 60 ＋ 62 ＝ 196
4. 64 ＋ 68 ＋ 85 ＋ 196 ＝ 413（根）
最佳归并树：根 413 的四个孩子为 64、68、85、196；64 的孩子为 9、17、18、20；17 的孩子为 0（虚段）、3、6、8；196 的孩子为 30、44、60、62。
$\text{WPL}=(3+6+8)\times3+(9+18+20+30+44+60+62)\times2+(68+85)\times1=51+486+153=690$ ⛳3
::note
- {{扣|没补虚段}}：直接拿 12 段做 4 路合并，最后一次只剩 3 段，树不是最优，WPL 会变大。
- 验算：合并结果之和 $17+64+196+413=690$，与按深度算的一致。
- 虚段长度为 0，放在最深一层，对 WPL 没有贡献。
::

#43
::think
1. 行数 ＝ 容量 ÷ 行长，组数 ＝ 行数 ÷ 路数；标记 ＝ 32 − 组号位 − 块内位。
2. 标记阵列每项：标记 ＋ 有效位 ＋ LRU 替换位（4 路 2 位）＋ 回写法才有的脏位。
::paper
解　(1) 行数 $64\text{KB}/128\text{B}=512$ 行；组数 $512/4=128$ 组。⛳3
(2) 每行一个标记项，共 512 个。块内地址 $\log_2128=7$ 位，组号 $\log_2128=7$ 位，标记位长度 $32-7-7=18$ 位。⛳4
(3) 全写法：每项 ＝ 标记 18 ＋ LRU 2 ＋ 有效位 1 ＝ 21 位，共 $512\times21=10752$ 位。⛳3
回写法：每项再加 1 位脏位，22 位，共 $512\times22=11264$ 位。⛳3
::note
- 全写（直写）法不需要脏位；回写法要用脏位判断换出时要不要写回主存。
- {{扣|替换位}}：本题提示了 LRU 用 2 位，漏掉会扣分；若是随机替换则不加。

#44
::think
1. 指令 `ADD R1, (R2)`：R1 ＋ 主存[R2] → R1。
2. 这条通路的 ALU 两个输入各有锁存器 LA、LB ⟹ 两个操作数分别打进 LA、LB，再一拍相加写回 R1。
3. 取指部分是公共操作：PC → MAR → 读主存 → MDR → IR，PC＋1 要写出来。
::paper
解　取指令（含 PC 自增）：⛳4
1. (PC) → MAR
2. M(MAR) → MDR
3. (PC) + 1 → PC
4. (MDR) → IR，操作码送控制器译码
执行：⛳6
5. (R1) → LA
6. (R2) → MAR
7. M(MAR) → MDR
8. (MDR) → LB
9. (LA) + (LB) → R1
::note
- PC＋1 可以经 ALU 完成（PC 送一个锁存器、C0＝1 加 1），也可以在读主存的同时进行；写成第 3 步单独一拍不扣分。
- (R1) → LA 可以与取操作数的步骤交换次序，只要在相加之前完成；不能和别的数同一拍上内部总线。
- {{扣|漏取指}}：题目明确要求写出取指令及 PC 自增的全过程。
::

#45
::think
1. 箱子 N 个位置被车架、车轮共用 ⟹ 若车架把位置占满，工人 3 拿不到车轮、工人 2 放不进车轮 ⟹ 死锁。
2. 防死锁：车架最多 N−2 个（给两个车轮留位），车轮最多 N−1 个（给车架留位）⟹ 两个额度信号量 s1＝N−2、s2＝N−1。
3. 再加常规的 empty＝N、frame＝0、wheel＝0。
::paper
解　信号量：⛳2
`semaphore empty = N;`　// 箱中空位
`semaphore frame = 0, wheel = 0;`　// 箱中车架数、车轮数
`semaphore s1 = N-2, s2 = N-1;`　// 车架、车轮的数量上限
```
工人 1:
do {
    加工一个车架;
    P(s1);  P(empty);
    车架放入箱中;
    V(frame);
} while (1);

工人 2:
do {
    加工一个车轮;
    P(s2);  P(empty);
    车轮放入箱中;
    V(wheel);
} while (1);
```
⛳3
```
工人 3:
do {
    P(frame);  箱中取一个车架;  V(empty);  V(s1);
    P(wheel);  P(wheel);  箱中取二个车轮;
    V(empty);  V(empty);  V(s2);  V(s2);
    组装为一台车;
} while (1);
```
⛳3
::note
- {{扣|没防死锁}}：只写 empty/frame/wheel 三个信号量是普通生产者—消费者，会在「箱子被一种零件占满」时死锁，只能拿部分分。
- 取零件不需要互斥信号量的前提是「取放各占独立位置」；若题目强调箱子一次只许一人操作，再加 mutex＝1 包住放入、取出动作。
- 额度信号量在取走时 V 回去，表示又可以放一个同类零件。
::

#47
::think
1. 非持续：每个对象都要「握手 1 RTT ＋ 请求响应 1 RTT（第三次握手捎带请求）＋ 发送时延」。
2. 持续、非流水线：只握手一次；之后每个对象「请求 1 RTT ＋ 发送时延」，一个收完才发下一个请求。
3. HTML 文件发送时延忽略，gif 每个 35ms。
::paper
解　(1) 非持续连接：⛳4
取 HTML：建连 150 ＋ 请求响应 150 ＝ 300ms（第三次握手捎带请求）；
每个 gif：$150+150+35=335$ms；
总时间 $300+10\times335=3650$ms。
(2) 持续连接（非流水线）：⛳5
建连 150ms，取 HTML 150ms，之后每个 gif 一次请求响应 ＋ 发送 $150+35=185$ms；
总时间 $150+150+10\times185=2150$ms。
::note
- 若是持续 ＋ 流水线：10 个请求连发，只需 1 个 RTT 再加 10 个对象的发送时延，$150+150+150+350=800$ms。
- {{扣|捎带请求}}：题目第 3 条说第三次握手捎带请求，所以不再额外多一个 RTT；漏看这条会多算 11 个 RTT。
::
