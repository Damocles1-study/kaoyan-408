:::say
IP 把分组送到了主机，可主机上跑着很多程序，这个分组给谁？而且 IP 不可靠，丢了怎么办？这就是传输层的两件事：把数据交给正确的进程，以及（TCP）让通信可靠。这一话讲 UDP 和 TCP 怎么建立、结束连接，下一话讲 TCP 怎么保证可靠。

== 传输层干什么 {base}
网络层是**主机到主机**，传输层是**进程到进程**（端到端）。一台主机上多个进程共用网络，发送时汇集叫**复用**，接收时分发叫**分用**，都靠**端口**。

**套接字**（socket）= IP + 端口，标识一个通信端点。

:::shu 端口
**熟知端口**（0–1023）：`20/21` FTP、`23` Telnet、`25` SMTP、`53` DNS、`69` TFTP、`80` HTTP、`110` POP3、`143` IMAP、`161` SNMP、`443` HTTPS。
**登记**（1024–49151）；**动态**（49152–65535）。
**TCP 用四元组（两端 IP:端口）标识连接；UDP 只用目的 IP 和目的端口分用**。
:::

== UDP {udp}
只在 IP 上加了端口和校验。没有握手、没有确认、没有重传。

@ bits([('源端口 16',16),('目的端口 16',16),('长度 16',16),('校验和 16',16)],unit='',cap='UDP 首部 8 B')

:::shu UDP 特点
**无连接、尽力交付、面向报文**（不拆不合）、**无拥塞控制**、首部 8 B。适合实时音视频、DNS。
:::

既然不可靠，为什么还要？首部小、没有连接开销、丢了也不影响实时音视频；应用可以自己做可靠性。

=== 校验和怎么算
校验和要覆盖 UDP 首部和数据，还要在前面临时加一个 12 字节的**伪首部**（源 IP、目的 IP、协议号、UDP 长度）。伪首部不发送，只用于计算。它让接收方能发现「分组送错了地方」。

算法：

1. 校验和字段先置 0，全部数据按 16 位分组（奇数字节补 0）。
2. 把所有 16 位按**反码**相加（高位进位加回低位）。
3. 取反，放入校验和字段。
4. 接收方把全部（含校验和）反码相加，结果全 1 才正确。

例：两个 16 位数 `0x8000` 和 `0x8001`。相加得 `0x1 0001`，进位加回得 `0x0002`，取反得 `0xFFFD`。

UDP 校验和在 IPv4 中可选（全 0 表示不校验）。TCP 用同样的算法，但必须校验。它只能发现错误，发现就丢弃，**不保证可靠**。

== TCP 首部 {tcp}
TCP 把应用数据看成字节流，每个字节都有序号。**面向连接、可靠、全双工、点对点**。

@ bits([('源端口 16',16),('目的端口 16',16)],unit='')
@ bits([('序号 seq 32',32,'gd')],unit='')
@ bits([('确认号 ack 32',32,'gd')],unit='')
@ bits([('首部长 4',4),('保留',6),('URG ACK PSH RST SYN FIN',6,'bk'),('窗口 16',16,'bu')],unit='',cap='首部长（数据偏移）以 4 B 为单位；窗口 rwnd 是我还能收多少')
@ bits([('校验和 16',16),('紧急指针 16',16)],unit='',cap='最小首部 20 B。选项里有 MSS')

:::shu 字段语义
**seq**：本段数据的第一个字节的序号。
**ack**：期望收到的下一个字节的序号（==累积确认==），ACK=1 才有效。
**SYN、FIN** 各占一个序号。
**纯 ACK 不占序号**。
**MSS**：最大段长，只算数据部分，握手时协商。
:::

走一遍序号：甲发 seq=100，带 200 字节，下一段 seq=300。乙全收到就回 ack=300，意思是「300 之前我都有了，下面要 300」。

如果甲连发三段（100、300、500），第二段丢了：乙收到第一段回 ack=300；收到第三段时第二段还没到，仍回 ack=300。累积确认只确认连续的部分。

**双向传数据时**，甲发出的 seq 等于乙最后的 ack，甲发出的 ack 等于乙的 seq 加乙的数据长度。

**标志位**：`SYN` 建连、`FIN` 释放、`ACK` 确认有效、`RST` 复位（异常，立即断开）、`PSH` 尽快交给应用、`URG` 紧急。

:::recall seq 和 ack 分别是什么？SYN 占序号吗？纯 ACK 呢？
seq 是本段第一个字节的序号；ack 是期望的下一字节。SYN、FIN 占一个序号；纯 ACK 不占。
:::

== 三次握手 {hs}
建立连接要交换初始序号，并确认双方的收发都正常。

@ seq(['客户','服务器'],[(0,1,'SYN=1, seq=x'),(1,0,'SYN=1, ACK=1, seq=y, ack=x+1'),(0,1,'ACK=1, seq=x+1, ack=y+1')],cap='第三次可以携带数据；SYN 不携带数据但消耗一个序号')

:::shu 握手要点
**为什么三次**：确认双方的发送和接收都正常，防止旧的连接请求造成错误。如果只有两次，一个滞留的旧 SYN 到达后，服务器就会白白建立连接。
**服务器的资源**：第二次握手后分配（SYN 洪泛攻击就利用这一点）。
**状态**：`LISTEN → SYN-RCVD → ESTABLISHED`。
:::

序号为什么不从 0 开始？防止和旧连接的序号混淆。

== 四次挥手 {fin}
TCP 全双工，两个方向要分别关闭。

@ seq(['客户','服务器'],[(0,1,'FIN=1, seq=u'),(1,0,'ACK, ack=u+1'),('note',1,'半关闭：服务器还能继续发'),(1,0,'FIN=1, seq=w, ack=u+1'),(0,1,'ACK, ack=w+1'),('note',0,'TIME-WAIT：等 2MSL')],cap='四次挥手')

中间的 ACK 和 FIN 能不能合并？能。如果服务器也没数据要发，就是三次。

**半关闭**：一方说「我不发了」，对方还可以继续发，它还能收。

:::shu 为什么要 TIME-WAIT
① 保证最后一个 ACK 到达（丢了对方会重发 FIN，可以重发 ACK）。② 让本连接的旧报文都消失，不干扰新连接。
**TIME-WAIT = 2MSL，主动关闭方才有**。
:::

:::shu 连接管理的时间（以 RTT 计）
**建立**：发起方收到第二次握手 = **1 RTT**，此后就能发数据；对方收到第三次握手 = **1.5 RTT**。
**释放**（对方立即回 FIN+ACK 的最快情况）：对方进入 CLOSED = **1.5 RTT**；发起方进入 CLOSED = **1 RTT + 2MSL**。
:::

:::recall 不看图，写出三次握手的 SYN、ACK、seq、ack。TIME-WAIT 的两个理由？
SYN=1,seq=x；SYN=1,ACK=1,seq=y,ack=x+1；ACK=1,seq=x+1,ack=y+1。保证最后的 ACK 能到；让旧报文消失。
:::

:::domain
**首部：**seq 第一字节，ack 期望下一字节；SYN、FIN 占序号。
**握手：**SYN，SYN+ACK，ACK（可带数据）。
**挥手：**可能半关闭；TIME-WAIT 等 2MSL。
**UDP：**8 字节，伪首部参与校验。
:::
