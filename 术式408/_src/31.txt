:::say
主存比 CPU 慢几十倍。Cache 的办法是在中间放一小块 SRAM，把最近用过的东西抄一份。这一话要解决四件事：东西放哪（映射）、满了赶谁（替换）、写了怎么同步（写策略），以及怎么算一段程序的命中率。
:::

== 基本原理 {base}
CPU 要读一个地址，先问 Cache 有没有。有就是**命中**，几个周期拿走；没有就是**缺失**，去主存读。

关键是：缺失时不是只读那一个字节，而是把它所在的**一整块**（通常 32 或 64 字节）搬进来。因为空间局部性告诉我们，它的邻居很快也要用。主存和 Cache 都按同样大的块切分，主存里叫**块**，Cache 里叫**行**（line）。

Cache 对程序员完全透明，全部由硬件完成，所以读写 Cache 的动作程序里看不见。

:::shu 性能公式
**命中率** H = 命中次数 ÷ 总访问次数。
**先查 Cache，不命中再访问主存**：`T = H·Tc + (1−H)(Tc+Tm)`，等价于 `T = Tc + (1−H)·Tm`。
**同时访问**：`T = H·Tc + (1−H)·Tm`。
**带缺失的 CPI**：`CPI = CPI₀ + 每条指令访存次数 × 缺失率 × 缺失损失`。
:::

算一遍：Tc = 2 ns，Tm = 20 ns，H = 95%。先查后访：2 + 0.05×20 = 3 ns；同时访问：0.95×2 + 0.05×20 = 2.9 ns。两种方式差别在于缺失时要不要多花那个 Tc。

再算 CPI：不缺失时 CPI₀ = 2，平均每条指令访存 1.3 次，缺失率 2%，缺失损失 100 周期。CPI = 2 + 1.3×0.02×100 = 4.6。2% 的缺失率让速度慢了一倍多，所以命中率差一点点影响就很大。

:::recall 为什么 Cache 一次搬一整块？同时访问和先查后访的公式差在哪？
因为空间局部性，邻居很快要用。先查后访在缺失时多花一个 Tc。
:::

== 东西放哪：三种映射 {map}
Cache 行数远少于主存块数，所以必须规定：主存的某一块能放到 Cache 的哪些行。放的范围越宽，越不容易冲突，但查的时候要比较的也越多。

:::ana 停车场
**直接映射**：每辆车只能停指定车位（车牌尾号决定）。那儿有车就把它赶走，哪怕别处全空。找车最快。
**全相联**：随便停。利用率最高，但找车要把所有车位看一遍。
**组相联**：分成几个区，车牌决定去哪个区，区内随便停。是前两者的折中。
:::

每一行除了数据，还要存「这是主存的哪一块」，这就是**标记**（Tag），加上**有效位**说明这一行装没装东西。查找时取出行内标记和地址里的标记比较，相同且有效才算命中。

假设主存地址 32 位，块 64 B（2⁶），Cache 共 128 行（2⁷）：

@ steps([
 (bits([('Tag 标记',19,'bk'),('行号 Index',7,'gd'),('块内偏移',6)],bare=True),'<b>直接映射</b>：块内 6 位；行号 7 位（128 行）；其余 19 位是标记。行号 = 块号 % 行数。只比较 1 个标记，冲突最多。'),
 (bits([('Tag 标记',26,'bk'),('块内偏移',6)],bare=True),'<b>全相联</b>：没有行号，除块内都是标记。要同时比较所有行，冲突最少，硬件最贵。'),
 (bits([('Tag 标记',21,'bk'),('组号',5,'gd'),('块内偏移',6)],bare=True),'<b>4 路组相联</b>：128÷4 = 32 组，组号 5 位。组内比较 4 个。路数翻倍，组号少一位，标记多一位。')],'同一个地址的三种切法')

:::shu 地址划分三步
**① 块内偏移** = log₂(块大小)，==块大小要换算成「编址单位」==，按字编址和按字节编址结果不同。
**② 组号** = log₂(行数 ÷ 路数)。直接映射路数为 1，全相联组数为 1。
**③ 标记** = 地址总位数 − 前两者。
定位：`块号 = 地址 ÷ 块大小`，`组号 = 块号 % 组数`，`标记 = 块号 ÷ 组数`。
:::

用一个地址走一遍：地址 0x12345，块 64 B，128 行。

- 块号 = 0x12345 ÷ 64 = 1165，余 5，块内偏移是 5。
- **直接映射**：行号 = 1165 % 128 = 13，标记 = 1165 ÷ 128 = 9。
- **4 路组相联**：组号 = 1165 % 32 = 13，标记 = 1165 ÷ 32 = 36。CPU 到第 13 组，把 4 行的标记都和 36 比。
- **全相联**：标记就是 1165，和 128 行全比。

下面用同一段访问序列 `0 4 0 4 0 4` 比较：Cache 4 行，块大小 1 个单位。

@ cache_sim([0,4,0,4,0,4],4,1,1,'LRU','直接映射：0 和 4 抢同一行，每次都缺失')
@ cache_sim([0,4,0,4,0,4],4,2,1,'LRU','2 路组相联：同组两行正好放下，只缺失前两次')

这种「明明还有空行，却因为抢同一个位置被赶走」的情况，叫**冲突缺失**。还有两类：第一次访问必然缺失（**冷启动缺失**），Cache 整个太小装不下（**容量缺失**）。路数提高只减少冲突缺失。

:::shu Cache 总容量
每行 = 数据位 + 标记位 + 有效位(1) + 脏位(回写才有，1) + 替换位(LRU 才有，log₂路数)。
总容量 = 行数 × 每行位数。
:::

算一遍：上面的 4 路组相联，用回写和 LRU。每行 = 512（数据）+ 21（标记）+ 1（有效）+ 1（脏）+ 2（LRU）= 537 位。总共 128×537 = 68736 位。「64 B × 128 = 8 KB 的 Cache」说的只是数据部分，真实占用要更大。

:::recall 给你地址位数、块大小、行数、路数，怎么切？比较器要几个？
块内 = log₂块大小；组号 = log₂(行数/路数)；剩下是标记。比较器个数等于路数：直接映射 1 个，全相联等于行数。
:::

== 满了赶谁：替换算法 {repl}
只有全相联和组相联要选。直接映射只有一个位置，没得选。

|算法|怎么做|特点|
|随机|随便选一行|实现简单，不用局部性，效果也不算差|
|FIFO|赶走最早进来的|简单；但最早进来的可能正在频繁用|
|LRU|赶走最久没用的|符合局部性，最常用|
|LFU|赶走次数最少的|曾经常用但已不用的赶不走，还要计数|

**LRU 怎么用硬件实现**：每行一个计数器，n 路用 log₂n 位，记录「多少行比我新」。以 4 路（值 0~3）为例：

1. **命中**：这一行清 0，比它原来小的计数器加 1。
2. **缺失且有空行**：新块进空行清 0，其他有效行加 1。
3. **缺失且满**：赶走值为 3 的那行，新块清 0，其余加 1。

LRU 也有克星。2 路的一组，循环访问三个同组的块 A B C A B C：每次要的恰好是刚赶走的那个，全部缺失。这叫**抖动**。原因是这组同时要用的块比路数多。

:::recall 为什么 LRU 比 FIFO 好？什么时候 LRU 也会全部缺失？
LRU 用了时间局部性，FIFO 不看使用情况。循环访问的块数大于路数时，LRU 每次都赶走下一个要用的。
:::

== 写了怎么同步：写策略 {write}
读不会造成不一致，写才会：Cache 里改了，主存还是旧的。分写命中和写不命中两种情况。

**写命中**，也就是要写的块在 Cache 里：

- **全写**（write-through）：同时写 Cache 和主存。主存永远最新，但每次写都等主存太慢，所以中间加一个**写缓冲**（一小块 FIFO），CPU 写进缓冲就走，由缓冲慢慢写主存。
- **回写**（write-back）：只写 Cache，把这一行的**脏位**置 1。被替换时，脏的才写回主存。

**写不命中**，也就是要写的块不在 Cache 里：

- **写分配**：先把块调进 Cache，再写。它要靠后续的访问才划算，所以配回写。
- **非写分配**：只写主存，不调入。配全写。

:::shu 写策略
**全写 + 非写分配**；**回写 + 写分配**（现代常用）。
全写不需要脏位；回写每行加 1 位脏位。
:::

:::ana 记账
全写是每笔流水都立刻跑一趟银行，写缓冲相当于请个跑腿的。回写是先记在自己的小本子上，本子要被收走时才一次性结算。
:::

:::trap 回写时，主存可能是旧的
回写的主存和 Cache 可能不一致，所以替换时要写回。全写的 Cache 永远是干净的。
多核时每个核都有自己的 Cache，一个核写了，别的核手上的副本就过期了，这是**一致性问题**，硬件用协议解决。
:::

**多级 Cache**：L1 最小最快，常拆成指令 Cache 和数据 Cache，这样取指和读数据可以同时进行，消除[[22|结构冒险]]。L1 和 L2 之间常用全写（下一层还是 Cache，不算慢），L2 和主存之间常用回写（写主存实在太慢）。

:::recall 回写为什么要脏位？写分配为什么配回写？
脏位标记这一行改过，替换时才写回，没改过的直接丢。写分配把块调进来之后，后续写都能在 Cache 里完成，和回写的思路一致。
:::

== 一段 C 程序的命中率 {cprog}
前面的知识合起来，就能分析真实代码。方法只有一条：==按代码的访问顺序，判断每次访问的块是不是已经在 Cache 里==。

:::shu 算命中率的步骤
**① 算每块放几个元素**：块大小 ÷ 元素大小。
**② 看访问顺序**：顺序访问时，每块只在第一次访问时缺失。
**③ 读后写同一个元素**：写的那一次必命中，因为刚读进来。
**④ 跳着访问**：算相邻访问隔了多少块，算这些块落到哪些行，有没有互相赶走。
:::

看一个完整例子：`int a[32][32]`（4 字节一个），从块边界开始存放。Cache 直接映射，块 32 B（每块 8 个 int），16 行（共 512 B）。

**按行访问** `for i for j a[i][j]`：C 语言按行优先存放（[[05|下标映射]]），所以这就是连续地址。每 8 个元素缺失 1 次，1024 次访问缺失 128 次，缺失率 12.5%。

**按列访问** `for j for i a[i][j]`：相邻两次隔一行，也就是 32 个 int，128 B，恰好 4 块。块号 = 4i + ⌊j/8⌋，行号再对 16 取模。所以 i 每加 4 就落回同一行，这一列会反复赶走同一批行。到下一列 j=1 时，a[0][1] 虽然和 a[0][0] 同块，但那一块早被 a[28][0] 赶走了。**1024 次全部缺失，缺失率 100%**（程序模拟的结果也是这样）。

同样的数组、同样的 Cache，只把两层循环交换，命中率就从 87.5% 变成 0。这就是局部性的威力。

再看**读后写**：`a[k] = a[k] + 1`，每块 8 个 int，每个元素读写各 1 次，每块 16 次访问只有第 1 次缺失，缺失率 1/16 = 6.25%。

:::deep 容量够不够，什么时候才有影响
顺序访问时，如果只扫一遍，Cache 再小缺失率也不变，因为前面的块不会再用，被赶走也没关系。只有**同一块要再次访问**时，容量和映射方式才起作用。所以先问自己：被赶走的块还会不会再用？
:::

:::recall 交换两层循环为什么差这么多？
按行时相邻访问连续，同块的元素连续命中。按列时每次跳很远，同一列的块又抢相同的行，下一列再回来时块已被赶走。
:::

:::domain
**地址：**标记 | 组号 | 块内；路数翻倍，标记多一位。
**容量：**行数 × (数据 + 标记 + 有效 + 脏 + 替换)。
**写：**全写配非写分配，回写配写分配。
**C 程序：**顺序访问每块只缺一次；写紧跟读必命中。
:::
